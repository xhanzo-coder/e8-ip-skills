# 完整生产工作流

本文件只定义所有风格共享的流程。比例、五官、线条、媒介、参考顺序、正向锚点和失败条件必须从 `references/style-registry.json` 指向的选中风格定义读取，不在公共流程重复维护。

## 0. 识别任务与现有状态

先确定任务属于：创建人物、重设计人物、新增风格、衍生图、一致性审计、修复图片或局部工作流。

- 当前对话已有正式人物：直接作为身份真源。
- 新对话要求复用：运行 `scripts/character_pack.py resolve` 查找角色包。
- 找不到正式人物：请用户上传人物参考或先创建基础人物。
- 没有 `.creator-space`：不阻塞创建；只有人物正式确认后才创建最小共享目录。

同时确定当前交互状态：

| 状态 | 第一次响应 | 能否立即生图 |
|---|---|---|
| 首次创建且未指定风格 | 分析参考，展示全部内置风格目录和推荐并等待 | 不能 |
| 已选择风格的创建或重设计 | 展示人物设计方案卡并等待 | 默认不能 |
| 只查看或比较风格 | 展示全部内置风格目录 | 不能 |
| 明确测试候选风格 | 展示候选状态、覆盖缺口和单张校准方案并等待 | 默认不能 |
| 为正式人物新增风格 | 展示风格转换方案并等待 | 默认不能 |
| 已确认人物＋已确认风格的衍生图 | 简短复述本次变化和不可变项 | 用户明确要求生成时可以 |
| 只分析、比较、审计或写方案 | 交付判断或方案 | 不能 |

“帮我创建／设计个人 IP”“根据这张照片做一个角色”属于创建意图，不是直接生图指令。只有“直接生成”“不用看方案”“你决定并生成”等同时明确放弃方案确认并要求出图的表达，才算跳过方案展示；即使跳过，也必须先用一句话声明采用的人物方案，且不能跳过生成后的正式人物确认。

## 1. 查看输入并做人物分析

使用图片查看能力逐张检查输入，不依据文件名猜测。为每张图分配且只分配必要角色：

- `identity`：证明“是谁”。
- `primary style`：控制选中风格的核心视觉语法。
- `secondary style`：补充主参考缺少的局部规则。
- `edit-target`：用户明确要求在该位图上局部编辑时使用。

按 `analysis-framework.md` 输出：稳定身份锚点、需要角色化重构的部分、应舍弃的姿势背景与临时穿搭、真正需要核对的未知事实。不要让用户自己选择眼睛大小、线宽、头身比等专业参数。

## 2. 解析风格能力

从 `references/style-registry.json` 找到风格条目并读取其 `definition`。校验：

1. 用户请求的交付是否在 `supported_outputs`。
2. 若在 `unverified_outputs`，只能承诺单张验证候选，不能直接批量生成。
3. 根据 `reference_maturity` 决定是否需要先做窄范围测试。
4. 读取风格定义中的参考路由、Prompt 段、硬门和专属 Profile。
5. 若 `run_validator` 非空，本次适用任务必须执行对应运行契约。
6. `candidate` 只允许用户明确点名后的单张校准；不得进入正式目录、自动推荐、正式角色包或批量衍生。

## 2.5 首次风格发现

用户首次创建人物且没有明确指定内置风格、没有提供新的风格参考、也没有明确说“你帮我选”时，读取 `style-catalog.md` 并展示全部正式可见风格：

1. 先过滤出 `lifecycle_status=active` 且 `catalog_visible=true` 的风格；`candidate` 与 `deprecated` 不参与编号和推荐。
2. 使用过滤后每个风格的 `catalog_preview` 作为唯一目录预览，不自行从参考资产中换图。
3. 每个风格同时展示名称、核心视觉区别、最适合的用途、已验证产物和未验证产物。
4. 根据人物参考与用途标出一个“推荐”，但不得替用户选定。
5. 只问一个问题：选择某个风格，还是采用推荐。
6. 展示后必须停下；风格选择不等于人物方案确认，也不等于生图授权。

以下情况不展示完整目录：

- 用户明确说出某个内置风格或其别名：直接选中并进入人物方案。
- 用户提供新的风格参考：比较后进入对应内置风格或自定义风格流程。
- 用户明确说“你帮我选”“风格你决定”：Skill 选择一个，展示选中预览和理由后进入人物方案；不能静默选择。

用户明确点名 `candidate` 风格时，不展示正式目录；先说明它尚未成为内置正式风格、所有产物仍未验证、本轮只做一张校准样张。用户确认校准方案后才能建立运行目录并执行候选专属校验器。

用户按目录预览选择风格后，注册表中的 `catalog_primary_style` 成为默认 `primary style`；它必须与预览相同或是预览的已登记正面裁图。只有用户明确同意换用该风格的其他内部参考时才可改变；目录展示一种画法、生成时偷偷换另一种画法属于风格欺骗。

## 3. 提案与生图授权

### 创建或重设计基础人物

风格已经选定后，基于人物分析和 `auto-selection.md` 主动推荐，不把眼睛大小、线宽、头身比等专业决策交给用户。展示一张简短方案卡：

- 提取出的稳定或可能稳定身份锚点。
- 被判定为临时的服装、姿势、背景和光线。
- 服装采用保留、简化还是重新设计，以及理由。
- 首选人物方向、相似程度、风格和配色。
- 本轮只制作一张正面基础人物候选。

最后只问一个合并问题：事实是否需要纠正，若无问题是否按此方案生成。输出后必须停下，不创建运行目录、不保存 Prompt、不调用图片工具。用户明确确认生成后再进入第 4 步。

### 新增或校准风格

先展示风格转换方案：主风格参考、身份不可变项、风格允许变化项、禁止复制项和本次校准样张范围。用户确认后首次只制作一张正面校准样张；样张未确认前不得批量制作表情、动作、场景或三视图，也不得登记为正式风格。

### 已确认人物的衍生图

人物和风格基准均已确认、请求仅改变动作、表情、头像裁切、允许的换装或视角时，不重复人物方案确认。用一句话声明“保持什么，只改变什么”后直接执行。若请求会改变脸部语法、发型剪影、角色比例、招牌符号或核心服装身份，则改走基础人物重设计确认。

正式基础人物确认与新增正式风格确认永远不能跳过。全部确认语义按 `confirmation.md` 判断。

## 4. 建立运行目录

每次任务创建独立目录，不覆盖旧运行：

```text
visual-ip/<任务slug>/
├── analysis.md
├── plan.md
├── run-contract.json（风格注册表要求时）
├── prompts/
├── qa.md
└── 候选图片
```

`plan.md` 必须记录身份参考、主风格参考、可选辅助参考、禁止迁移项、相似程度、配色策略、交付类型和已知覆盖边界。生成前缺少 `plan.md` 或对应 Prompt 文件时不得调用图片工具。

## 5. 组装 Prompt 与生成前校验

按 `prompt-assembly.md` 保存本张候选的完整 Prompt。随后比较三处：

- `plan.md` 的参考图清单。
- Prompt 中的参考角色声明。
- 实际图片工具调用参数。

三者必须是同一组参考。支持多参考图的工具必须实际调用同时传入身份图和主风格参考；不能只在文字里声称参考。

若风格条目声明 `run_validator`，按对应运行契约创建 `run-contract.json` 并先通过 `--phase pre`。未通过不得烧图。

## 6. 生成候选

- 每张不同候选单独生成，不在一次调用中要求模型同时探索多种方向。
- 基础人物首次只生成一张正面候选，使用完整全身、中性背景和足够判断身份与风格的完成度；不要同时烧多张近似候选。第一张方向失败时，回到方案或 Prompt 修正后再生成下一张。
- 新风格首次只生成一张正面校准样张，保持身份连续和可比画幅，只改变风格方案允许改变的结构层级。
- 衍生图固定人物与风格，只改变当前动作、表情、服装或场景。
- 三视图先确认正面母图，再分别生成侧面和背面，最后组合。

## 7. 三层 QA

生成后把候选与主风格参考并排查看，并按 `quality-checklist.md` 写入 `qa.md`：

1. 人物身份层。
2. 风格语法层。
3. 当前任务层。

风格定义中的任一硬门失败，候选即拒绝。失败图保存为失败候选，但不得向用户介绍为“可确认版本”。若存在运行校验器，更新候选、QA 与正向锚点并通过 `--phase post`；未通过时状态只能是 `rejected`。

## 8. 交付、修改与保存

交付候选图、关键差异和一个明确确认问题：基础人物候选询问是否正式确定人物，风格校准样张先询问风格方向是否正确。修改前先更新 Prompt；不要直接在位图上反复涂改人物或风格真源。

用户明确确认基础人物后，按 `character-package.md` 调用 `scripts/character_pack.py save-character`。新增风格经单独确认后调用 `add-style`；人物或风格更新使用对应 update 命令并保留版本化备份。候选和失败图不进入共享角色包。
